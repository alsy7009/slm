# CircuitSight — Evaluation Results

*Last updated 2026-07-10. All numbers are from actual runs (captured from the Colab run outputs); see "How to reproduce".*

## TL;DR

Fine-tuning a 3B vision-language model on our circuit dataset produces **large gains in "reading"
the schematic** — identifying components (0.17 → 0.96), naming the reactive type (0.33 → 1.00),
locating parts with bounding boxes (grounding 0.00 → 0.84), and **answering honestly** on unreadable
values (0.00 → 1.00) — while **solving for the final number stays low** (answer accuracy 0.00 → 0.09).

Splitting the answer accuracy by how values are written shows *why*: the model scores **0%** when it
must do the **arithmetic** (numeric problems) but **~31%** when the answer is an **algebraic
expression** (symbolic problems — same reading and reasoning, no arithmetic). So the weakness is
*arithmetic*, not *circuit reasoning*. That is exactly the moat we set out to build (perception +
correct setup), with the arithmetic offloadable to a calculator.

## What we tested (so a reader who hasn't seen the data can understand it)

**Testing set = a held-out *synthetic* validation split** (`val_synthetic.jsonl`, **500 records**;
the training set is 9,500). The circuits are generated by the same procedural pipeline as training —
a numerical circuit solver produces the ground-truth labels — but this 5% split is **never seen during
training**. Each record is one **schematic image + one question**, paired with exact gold labels: the
component list, a bounding box per component, the topology, the correct final answer, and the
intermediate values (equivalent resistance, per-branch currents).

The set spans:

- **Circuit families:** DC-resistor networks (series/parallel, ~60%), reactive circuits (a capacitor or
  inductor at steady-state or t=0, ~25%), and **Wheatstone bridges** (non-series-parallel, solved by
  nodal analysis, ~15% — the hard case a generic model can't reduce).
- **Value modes** (how component values appear on the diagram):
  - **numeric** — real numbers (`220Ω`, `12V`); solving needs actual arithmetic.
  - **symbolic** — letters (`R1`, `R2`, `V`); the correct answer is an algebraic expression
    (`R_eq = R1 + R2`). Tests reading + reasoning **with no arithmetic**.
  - **mixed** — some numbers and some symbols in one circuit.
  - Training composition (9,500 records): numeric 5,271 / symbolic 2,750 / mixed 1,479.
- **Question types:** current, voltage, power, equivalent resistance, charge, energy.
- **Abstention cases (~8%):** the value in the image is deliberately illegible; the correct behavior is
  to answer `null` ("I can't read it") instead of fabricating a number.

**Decoding:** greedy / deterministic (`temperature=0`); `max_new_tokens` = 256 for Run A, 400 for Run B.

**Sample sizes** (each run scores the first *N* rows of the val split):

| Run | Model(s) | N rows | Composition |
|---|---|---|---|
| **A — base vs. fine-tuned** | base + tuned | 24 | 23 solvable + 1 abstention; 6 reactive |
| **B — value-mode split** | tuned only | 36 | 33 solvable (14 numeric, 13 symbolic, 6 mixed) + 3 abstention |

These are small samples (fast iteration on limited GPU time). Treat single values as indicative — e.g.
Run A's abstention metrics rest on **1** case and reactive-type on **6**. The **numeric-vs-symbolic gap
in Run B** is the robust headline: it holds across 14 vs 13 samples and is large.

## Metric glossary (plain language)

**Reading / perception**
- **component_accuracy** — right *number* of resistors and correct detection of a capacitor/inductor.
- **reactive_type_accuracy** — on reactive circuits, named the *correct* one (not capacitor↔inductor).
- **grounding_recall** — of the real components, fraction boxed on-target (box overlap ≥ 0.5).
- **grounding_precision** — of the boxes it drew, fraction that landed on a real component.
- **grounding_f1 / grounding_hallucination_rate** — combined P/R; fraction of boxes hitting nothing.

**Solving**
- **Req_accuracy** — equivalent resistance (a key intermediate) correct.
- **intermediates_accuracy** — *every* branch current correct.
- **answer_accuracy** — final answer correct (numeric within 3%, or symbolically equivalent).
- **step_verified_accuracy** — strict: components **and** R_eq **and** all intermediates **and** final
  answer all correct (a right answer via wrong steps does not count).
- **answer_accuracy_by_value_mode / _by_qtype** — answer accuracy split by numeric/symbolic/mixed and
  by question type.

**Honesty (abstention cases)**
- **honest_abstention_rate** — correctly said `null` on an illegible value (higher better).
- **fabrication_rate** — invented a number instead (lower better).
- **abstention_precision / recall** — when it abstained, was it truly illegible / of illegible cases,
  how often it abstained.

**Concepts**
- **concept_declared_rate / concept_hallucination_rate** — stated the concepts used / cited one the
  problem doesn't need (lower better).

## Key finding

The fine-tuned model **reads and sets up circuits well but cannot reliably do the arithmetic**:

- Perception jumps from near-zero to near-perfect: components 0.17 → 0.96, reactive type 0.33 → 1.00,
  grounding 0.00 → 0.84, and it learns to say "I can't read it" (honest abstention 0.00 → 1.00) instead
  of guessing.
- On **symbolic** problems — answer is an expression like `R_eq = R1 + R2`, requiring correct reading
  and reasoning but **no arithmetic** — it is right **~31%** of the time.
- On **numeric** problems — identical circuits requiring multi-step arithmetic — it is right **0%** of
  the time.

A model that failed at *reasoning* would score near 0 on symbolic too. Instead the gap is entirely on
the *arithmetic* step. This is the intended result: **the moat is perception + correct setup** (which
generic models fail at, as the base column shows), and **the arithmetic is offloadable to a
calculator/solver** — feeding the model's setup into a solver would lift numeric accuracy toward the
symbolic level.

**Caveats:** samples are small (abstention rests on 1 case in Run A); symbolic accuracy is 31%, not
near-perfect, so the claim is *relative* (reasoning ≫ arithmetic), not "reasoning is solved."
