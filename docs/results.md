# CircuitSight — Evaluation Results

*Last updated 2026-07-10. Numbers below are from actual runs; see "How to reproduce".*

## TL;DR

Fine-tuning a 3B vision-language model on our circuit dataset produces **large gains in
"reading" the schematic** (identifying components, their type, and where they are) and in
**answering honestly**, while **solving for the final number stays low**. Splitting the answer
accuracy by how the values are written shows why: the model scores **0%** when it must do the
**arithmetic** (numeric problems) but **~31%** when the answer is an **algebraic expression**
(symbolic problems, same reading/reasoning, no arithmetic). So the weakness is *arithmetic*, not
*circuit reasoning* — which is exactly the moat we set out to build (perception + correct setup),
with the arithmetic offloadable to a calculator.

## What we tested (so a reader who hasn't seen the data can understand it)

**Testing set = a held-out *synthetic* validation split** (`val_synthetic.jsonl`). The circuits are
generated by the same procedural pipeline as the training data (a numerical circuit solver produces
the ground-truth labels), but this 5% split is **never seen during training**. Every record is one
**schematic image + one question**, paired with exact gold labels: the component list, a bounding
box per component, the topology, the correct final answer, and the intermediate values (equivalent
resistance, per-branch currents).

The synthetic set spans:

- **Circuit families:** DC-resistor networks (series/parallel combinations, ~60%), reactive circuits
  (a capacitor or inductor evaluated at steady-state or t=0, ~25%), and **Wheatstone bridges**
  (non-series-parallel, solved by nodal analysis, ~15% — the hard case a generic model can't reduce).
- **Value modes** (how component values are written on the diagram):
  - **numeric** — real numbers (e.g. `220Ω`, `12V`); solving requires actual arithmetic.
  - **symbolic** — the values are letters (e.g. `R1`, `R2`, `V`); the correct answer is an algebraic
    expression (e.g. `R_eq = R1 + R2`). This tests reading + reasoning **without arithmetic**.
  - **mixed** — some numbers and some symbols in the same circuit.
- **Question types:** current, voltage, power, equivalent resistance, charge, energy.
- **Abstention cases (~8%):** the value in the image is deliberately illegible; the correct behavior
  is to answer `null` ("I can't read it") rather than fabricate a number.

**Decoding:** greedy / deterministic (`temperature=0`, `max_new_tokens=400`), so results are
reproducible.

**Sample sizes** (each run subsamples the first *N* rows of the val split):

| Run | Model(s) | N rows | Composition |
|---|---|---|---|
| **A — base vs. fine-tuned** | base + tuned | 24 | 23 solvable + 1 abstention; 6 reactive |
| **B — value-mode split** | tuned only | 36 | 33 solvable (14 numeric, 13 symbolic, 6 mixed) + 3 abstention |

These are small samples (fast iteration on limited GPU time), so treat single-metric values as
indicative; the **numeric-vs-symbolic gap in Run B is large enough to be meaningful** despite the n.

## Metric glossary (plain language)

**Reading / perception**
- **component_accuracy** — did it get the right *number* of resistors and correctly detect whether a
  capacitor/inductor is present?
- **reactive_type_accuracy** — on capacitor/inductor circuits, did it name the *correct* one (not
  confuse a capacitor for an inductor)? The headline "does it actually see the part" number.
- **grounding_recall** — of the components really in the image, what fraction did it draw a box around
  that lands on the real part (overlap ≥ 0.5)?
- **grounding_precision** — of the boxes it drew, what fraction landed on a real component?
- **grounding_f1 / grounding_hallucination_rate** — combined P/R score; and fraction of boxes that hit
  nothing.

**Solving**
- **Req_accuracy** — did it get the equivalent resistance (a key intermediate) right?
- **intermediates_accuracy** — did it get *every* branch current right?
- **answer_accuracy** — is the final answer correct (numeric within 3% tolerance, or symbolically
  equivalent)?
- **step_verified_accuracy** — strict: components **and** R_eq **and** all intermediates **and** the
  final answer all correct (a right answer via wrong steps does not count).
- **answer_accuracy_by_value_mode / _by_qtype** — the above answer accuracy split by numeric/symbolic/
  mixed, and by question type.

**Honesty (abstention cases)**
- **honest_abstention_rate** — how often it correctly said `null` on an illegible value (higher better).
- **fabrication_rate** — how often it invented a number instead (lower better).
- **abstention_precision / recall** — precision: when it abstained, was it truly illegible; recall: of
  illegible cases, how often it abstained.

**Concepts**
- **concept_declared_rate / concept_hallucination_rate** — did it state the physics concepts it used;
  did it cite one the problem doesn't need (lower better).

## Results

### Run A — Base vs. fine-tuned (n = 24 val records)

Fine-tuning turns "reading the circuit" from near-chance into near-perfect, while solving stays low.

| Metric | Base | Fine-tuned | Δ |
|---|---|---|---|
| component_accuracy | 0.167 | **0.958** | +0.792 |
| reactive_type_accuracy | 0.333 | **1.000** | +0.667 |
| Req_accuracy | 0.000 | 0.182 | +0.182 |
| answer_accuracy | ~0 | 0.087 | — |
| step_verified_accuracy | ~0 | 0.087 | — |

Answer accuracy by question type (fine-tuned): resistance 0.00, current 0.13, voltage 0.20, power /
charge / energy 0.00.

> Note: the full Run A table also included grounding (precision/recall/F1), fabrication vs.
> honest-abstention, concept scoping, and abstention precision/recall. Those exact numbers were not
> captured in text and are not reproduced here — re-running §9 (base vs. tuned) regenerates the
> complete table. Qualitatively, the perception, grounding, and honesty axes showed the same large
> base→tuned jump as component/reactive-type above.

### Run B — Fine-tuned answer accuracy by value mode (n = 36; 33 solvable)

The diagnostic that isolates the failure. Same circuit families and reading task; the only difference
is whether the final answer requires arithmetic.

| Value mode | Answer accuracy | n | What it requires |
|---|---|---|---|
| **numeric** | **0.000** | 14 | read + reason + **arithmetic** |
| **symbolic** | **0.308** | 13 | read + reason, **no arithmetic** |
| **mixed** | 0.333 | 6 | mostly reasoning |
| overall | 0.182 | 33 | |

## Key finding

The fine-tuned model **reads and sets up circuits well but cannot reliably do the arithmetic**:

- It identifies components and their type almost perfectly (0.167 → 0.958; reactive-type 0.333 → 1.000).
- On **symbolic** problems — where the answer is an expression like `R_eq = R1 + R2`, requiring correct
  reading and reasoning but **no arithmetic** — it is right **~31%** of the time.
- On **numeric** problems — identical circuits but requiring actual multi-step arithmetic — it is right
  **0%** of the time.

A model that failed at *reasoning* would score near 0 on symbolic too. Instead the gap is entirely on
the *arithmetic* step. This is the intended result: **the moat is perception + correct setup** (which
generic models fail at), and **the arithmetic is offloadable to a calculator/solver** — feeding the
model's setup into a solver would lift numeric accuracy toward the symbolic level.

**Caveats:** samples are small; symbolic accuracy is 31%, not near-perfect, so the claim is *relative*
(reasoning ≫ arithmetic), not "reasoning is solved". Runs A and B report slightly different overall
answer accuracy (0.087 vs 0.182) because they sampled different numbers of rows.
